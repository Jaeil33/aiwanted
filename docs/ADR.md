# Architecture Decision Records

## 철학
- 재미는 과장으로, 신뢰는 계산으로. 숫자는 코드가 정확히 계산하고, 과장은 '만화 모드' 라벨을 달 때만 한다.
- 9/20에 휴대폰에서 끝까지 도는 한 판이 먼저다. 모든 기능은 AI나 데이터가 없어도 동작하는 대체 경로를 가진다.
- 원자료는 우리 것이 아니다. 필요한 최소 요약만 앱에 싣고 출처를 밝힌다.

### ADR-001: Next.js 대신 Vite + React SPA
**결정**: Vite 8 + React 19 + TypeScript 6.0 정적 번들. 서버 로직은 `api/` 서버리스 함수 두 개(AI 프록시)뿐이다.
**이유**: 확률 엔진이 브라우저에서 돌기 때문에 서버 렌더링이 필요 없다. 정적 번들은 단일 HTML 아티팩트 미리보기와 어느 정적 호스팅에도 그대로 올라간다. `vite-plugin-singlefile`로 데이터까지 한 파일에 담을 수 있다.
**트레이드오프**: 공유 링크별 OG 이미지를 서버에서 만들 수 없다(공유 카드는 클라이언트 캔버스로 만든다). 하네스 템플릿의 Next.js 예외(page.tsx 등)가 TDD 가드에 적용되지 않으므로 모든 .ts/.tsx에 테스트 파일을 둔다.

### ADR-002: 확률은 정확 계산, 재생만 표본
**결정**: 타석 분포(오즈비 매칭) → 반이닝 마르코프 질량 전파(아웃·주자·타순·득점) → 경기 동적 계획(이닝·점수차·양 팀 타순, 11회 무승부)으로 정확한 확률을 낸다. 볼카운트는 리그 카운트별 투구 결과 표를 매치업에 맞게 보정한 흡수 마르코프 체인이다. 재생(한 구·타석·경기 끝까지)만 시드 난수로 표본을 뽑는다.
**이유**: TMI 효과는 0.1%p 단위로 작다. 몬테카를로 잡음이 효과보다 크면 게임의 핵심 문장("짜장면 하나로 +0.6%p")이 흔들린다. 같은 입력에 같은 숫자가 나와야 공유와 검증이 가능하다.
**트레이드오프**: 주루·병살 확률은 고정 상수(프로토타입 `buildTransitions`)이고, 이후 반이닝은 불펜 합성 선수로 단순화한다. 선수 교체·대타·도루는 모델에 없다.

### ADR-003: 숫자는 엔진, 말은 AI
**결정**: AI는 자유 문장을 `KnobPart`/`MeasuredPart`와 한 줄 해설로 번역하고, 판정 때는 evidence 조회 결과를 설명만 한다. 모든 AI 출력은 `normalize.ts`로 검증(손잡이·대상 조합, 세기 −3~3 정수, 최대 3개, 글자 수)하고, 실패하면 규칙 해석으로 대신한다.
**이유**: 심사 기준인 'AI 활용 적절성'은 AI가 꼭 필요한 곳(엉뚱한 자연어 이해와 설명)에 쓰였는지다. 확률을 LLM이 만들면 틀려도 검증할 수 없다.
**트레이드오프**: 14개 손잡이와 실측 변수 밖의 새 메커니즘은 표현할 수 없다. 규칙 해석은 AI보다 덜 재밌다.

### ADR-004: 실측 변수는 팀-경기 포아송 모델 + 시간 순 검증
**결정**: 2021–2026 정규시즌 팀-경기 행(그 팀의 득점)에 `log μ = 공격(팀·시즌) + 수비(상대·시즌) + 구장 + β·x` 포아송 GLM을 IRLS로 적합한다(요인 효과에만 작은 릿지). x = 기온·바람 세기·경기 전 3시간 강수·낮 경기·주말·원정 이동 거리·휴식일 다음 경기·상대 선발 짧은 휴식·상대 선발 긴 휴식·(참고용) 홈. β는 2021–2025로만 추정하고, 2026 경기에서 이탈도 개선량(경기 단위 부트스트랩 95% 구간)으로 검증한다. 판정: 학습 95% 구간이 0을 벗어나고 2026 개선 구간 하한이 0보다 크면 `real`, 둘 중 하나만 만족하면 `maybe`, 둘 다 아니면 `useless`. 앱은 득점 배수를 리그 평균 타선의 득점 탄력성으로 나눠 공격 벡터 크기로 바꿔 적용한다.
**이유**: 선수 단위로 쪼개면(예: 특정 투수의 낮 경기) 표본이 작아 잡음뿐이다. LG Aimers에서 멘탈·클러치 피처가 모두 효과가 없거나 오히려 점수를 떨어뜨린 교훈이다. 팀-경기는 5천 경기가 넘어 작은 효과도 구간으로 말할 수 있다. 학습·검증 분리는 LG Aimers의 walk-forward 방식 그대로다.
**트레이드오프**: 팀 단위 효과를 모든 타석에 똑같이 나눠 적용한다. 바람 방향·습도·구장 방향은 없다. 고척돔은 날씨 변수를 0으로 둔다. 선발 휴식일은 선발 이름+팀으로 계산해 기록 누락에 약하다.

### ADR-005: 데이터 권리와 실명
**결정**: 네이버 비공식 API·Open-Meteo 원자료와 생성물은 `data/`에만 두고 커밋하지 않는다. 앱에는 장면에 필요한 최소 요약(선수 상대 능력치, 장면 투수의 투구 표본, 장면 상태)만 싣고 화면에 출처를 적는다. 선수는 텍스트 실명만 쓰고 사진·구단 로고·엠블럼 URL은 쓰지 않는다. 실존 선수에 대한 민감한 TMI는 AI와 규칙 양쪽에서 거부한다.
**이유**: 공식 기록 권리는 KBO와 데이터 사업자에게 있고, 비공식 API 원자료 재배포는 분쟁 전례가 있다. 저장소가 공개라서 커밋이 곧 재배포다.
**트레이드오프**: 저장소만 받아서는 앱 데이터를 재현할 수 없다(`npm run data`에 원자료가 필요). 선수 얼굴 없는 연출이 된다.

### ADR-006: AI 프로바이더 3단 구성
**결정**: (1) 아티팩트 미리보기: `claude.use('sample')`의 `json`으로 해석(modelTier `quick`), `tools`로 판정(modelTier `default`). (2) 배포: `api/interpret.ts`, `api/verdict.ts`가 서버 환경변수 키로 Anthropic Messages API를 부른다. 모델은 환경변수 `TMI_MODEL_INTERPRET`(기본 `claude-haiku-4-5-20251001`), `TMI_MODEL_VERDICT`(기본 `claude-sonnet-5`). 입력 80자, 출력 토큰, IP당 분당 호출 수를 제한한다. (3) 없음: 규칙 해석·규칙 판정. 배포 경로는 해석 8초·판정 60초 제한 시간을 넘으면 규칙으로 대신한다. 아티팩트 경로는 첫 호출에서 보는 사람의 동의를 기다리므로 플랫폼 지침대로 페이지 쪽 제한 시간을 두지 않고, 오류 코드가 오면 규칙으로 대신한다. 어느 경로도 코드에서 재시도하지 않는다.
**이유**: 미리보기에서는 키 없이 실제 AI를 쓸 수 있고, 배포에서는 투표 참여자 누구나 계정 없이 써야 한다. 해석은 짧은 JSON이라 빠른 모델로 충분하고, 판정은 도구 호출과 설명 품질이 중요하다.
**트레이드오프**: 배포 비용과 남용 위험(호출 제한으로 완화), 프로바이더마다 응답 모양이 다름(normalize로 흡수).

### ADR-007: 허용 의존성
**결정**:
- dependencies: `react`, `react-dom`
- devDependencies: `vite`, `@vitejs/plugin-react`, `typescript@~6.0.3`, `vitest`, `jsdom`, `@testing-library/react`, `@testing-library/dom`, `@testing-library/jest-dom`, `@testing-library/user-event`, `eslint`, `@eslint/js`, `typescript-eslint`, `eslint-plugin-react-hooks`, `globals`, `vite-plugin-singlefile`, `tsx`, `@types/react`, `@types/react-dom`, `@types/node`
- Python(`pipeline/requirements-dev.txt`): `numpy`, `pytest`
**이유**: TypeScript 7은 typescript-eslint가 아직 지원하지 않는다(`<6.1.0`). 차트·상태관리·스타일 라이브러리 없이 캔버스·SVG·useReducer로 충분하다.
**트레이드오프**: 차트와 애니메이션을 직접 그린다.

### ADR-008: 하네스 병렬 실행
**결정**: `0-setup`(스캐폴딩·공용 타입) 뒤에 `1-engine`, `2-data`, `3-stage`, `4-ai`를 각각 별도 git worktree에서 동시에 실행하고, 통합 브랜치에서 합친 뒤 `5-app`, `6-release`를 순서대로 실행한다. 로컬 자동 모드는 권한 우회(`--dangerously-skip-permissions`) 세션 생성을 막으므로, phase는 권한 검사를 그대로 받는 격리 서브에이전트가 `execute.py`와 같은 규칙(step 파일 순서, AC 실행, `index.json` 상태·summary·타임스탬프 기록, step마다 `feat(<phase>): step N — <name>` 커밋)으로 실행한다. `scripts/execute.py`는 사람이 직접 돌릴 때를 위해 Windows 보정(stdin UTF-8 프롬프트, 1시간 제한 시간 기록)을 유지한다.
**이유**: 공용 계약(`src/types`, `src/domain`, 이 문서들)이 먼저 고정되면 네 층은 서로의 코드를 읽을 필요가 없다. 권한 우회 없이도 step 파일·AC·기록이라는 하네스의 검증 구조는 그대로 지킬 수 있다.
**트레이드오프**: step마다 새 세션을 띄우는 대신 phase 단위 세션이라 앞 step의 맥락이 이어진다. 통합할 때 `phases/index.json` 충돌을 손으로 푼다. worktree마다 `node_modules`와 `.venv`를 따로 만든다.

### ADR-009: 만화 모드
**결정**: 만화 모드는 모든 TMI 효과의 로그 오즈를 6배로 키우고 상한을 0.45에서 1.6(최대 약 5배)으로 넓힌다. 화면에 "만화 모드: 효과 6배 과장"을 항상 표시하고, 결과와 공유 카드 이미지 안에도 모드를 새긴다.
**이유**: 현실 크기(±1%p 안팎)는 정직하지만 첫 경험의 '와'가 약하다. 두 모드의 차이 자체가 "쓸모없는 변수는 실제로 작다"는 메시지가 된다.
**트레이드오프**: 과장 수치가 캡처돼 사실처럼 퍼질 수 있다. 이미지 안에 라벨을 새겨 완화한다.

### ADR-010: 휴대폰 우선 단일 테마
**결정**: 390px 세로 화면을 기준으로 설계하고 1024px 이상에서 2단으로 넓힌다. 야간 경기 중계 그래픽의 단일 다크 테마로 고정한다(라이트 테마 없음).
**이유**: 투표가 휴대폰 인증이라 대부분 휴대폰으로 들어온다. 중계 화면의 LED·조명 느낌은 어두운 바탕에서만 산다.
**트레이드오프**: 밝은 곳 가독성은 대비 기준(본문 4.5:1 이상)으로만 보장한다.

### ADR-011: 게임형 화면과 프리미엄 UI (ADR-010의 레이아웃, UI_GUIDE 원칙 대체)
**결정**: 플레이·결과 화면은 사이트 머리말·푸터 없이 전체 화면 게임 레이아웃으로 그린다. 로비(첫 화면)·판정소·만든 이유는 하단 탭바를 쓴다. 휴대폰 세로(390px) 기준이고, 1024px 이상에서는 2단 대시보드 대신 가운데 최대 480px 게임 열을 두고 양옆은 어두운 경기장 배경으로 채운다. 움직임은 결과를 알리는 순간(볼·스트라이크 콜, 승률 게이지 이동, TMI 카드 뒤집기, 1,000경기 점 채우기, 로비 조명 켜기)에만 쓰고 `prefers-reduced-motion`에서 끈다. 시각 기준은 `docs/design/nightgame/` 시안과 `docs/UI_GUIDE.md`다.
**이유**: 사용자 평가가 "UI가 멋없고 실제 게임 같지 않다"였다. 설명 문단·3단 표·패널을 쌓은 문서형 화면은 한 판의 긴장감을 주지 못한다. 투표와 심사는 첫 화면 인상에서 갈린다.
**트레이드오프**: 데스크톱에서 한 화면에 보이는 정보가 줄어든다. 기존 화면·컴포넌트와 그 테스트를 대부분 새로 쓴다.

### ADR-012: 중견수 쪽 중계 카메라 시점 (ADR-005 연출 보강)
**결정**: 경기장 캔버스는 포수 뒤 시점 대신 TV 중계의 중견수 쪽 망원 카메라 시점으로 그린다(투수 등, 타자·포수·주심이 한 화면). PTS 궤적은 같은 경기장 좌표계에서 새 카메라로 투영한다. 볼·스트라이크·결과 콜은 캔버스 배너 대신 DOM `Callout` 컴포넌트가 그린다(aria-live, 글꼴, 모션 제어). 문서가 숨겨지면(`visibilitychange`) 진행 중인 연출을 즉시 끝낸다.
**이유**: 한국 야구 중계에서 가장 익숙한 화면이라 '진짜 경기'로 읽힌다. 기존 시점은 앞쪽 타자가 화면 절반을 가렸다. 숨은 탭에서 requestAnimationFrame이 멈춰 재생이 멈춘 것처럼 보였다.
**트레이드오프**: 공의 좌우 휨이 덜 보인다(스트라이크 존 오버레이와 투구 위치 표시로 보완). 렌더러·카메라 계산과 테스트를 다시 쓴다.

### ADR-013: 해석은 항상 답한다 (ADR-003 보강)
**결정**: 민감 주제가 확실할 때만 거부하고, 그 밖의 모든 입력은 효과를 1개 이상 만든다. 규칙 해석 순서는 다음과 같다.
1. 입력 정리: 유니코드·반복 문자, 초성·오타, 영어·이모지, 숫자와 단위.
2. 안전 판정: 범주별 사전, 주체 확인(선수·가족인지, 관중·동물·음식 이름인지), 허용 관용구(마약김밥, 자살 스퀴즈, 타격감이 죽었다). 결과는 block/review/allow.
3. 절 나누기: 최대 3개.
4. 대상 추론: 실명·이름·타선 소속·역할어·팀 별칭·동사 순서.
5. 개념 사전×방향×세기: 부정어·강도어·숫자 구간을 반영한다.
6. 끝까지 못 찾으면: 문장 분위기(분위기가 없으면 문장 해시)로 방향을 정해 대상의 집중력이나 팀 분위기에 ±1을 넣는다. 범위는 이번 타석, 등급은 '상상'이고 "딱 맞는 규칙이 없어 문장 분위기로 살짝 이었어요"라고 밝힌다.

AI 경로도 같은 원칙을 따른다.
- 프롬프트는 효과를 1개 이상 요구한다.
- `normalize`는 버리기 전에 복구한다(동의어, kind 추론, 숫자 추출, 코드펜스 제거).
- 복구 뒤에도 효과가 0개면 AI 해설은 두고 효과는 규칙으로 채운다.
- AI가 거부했는데 로컬 안전 판정이 allow면 규칙 해석을 쓴다.
- review는 AI가 판단하고, AI가 없으면 거부한다.

거부·실패 때 입력창을 비우지 않고, 거부된 문장은 TMI 칸을 차지하지 않는다.
**이유**: 규칙 해석은 무해한 입력 237개 중 27%에서만 뜻에 맞는 효과를 냈다. 52%는 효과가 없었다. 무해한 경계 문장 25개 중 14개를 거부했고, 민감 문장 33개 중 23개는 통과시켰다. AI가 낸 합리적인 응답도 `normalize`가 효과를 전부 버리면 알림 없이 ±0.00%p가 됐다. 사용자 요구는 "어떻게 입력하든 알아서 잘하라"다.
**트레이드오프**: 억지 해석이 늘어난다('상상' 등급과 문구로 밝힌다). 사전을 계속 관리해야 한다. 공개 저장소이므로 테스트 말뭉치에는 가상 이름만 쓰고 실존 선수 이름과 민감 문장을 함께 두지 않는다.

### ADR-014: 장면 데이터는 투구 시점 상태를 따른다 (ADR-005 보강)
**결정**: 장면을 만드는 규칙은 다음과 같다.
- **투수**: 타석 첫 투구의 `currentGameState.pitcher`.
- **타선**: 교체 기록(`outPlayerTurn`)을 반영한, 그 시점에 실제로 뛰던 선수.
- **장면 id**: 결과를 드러내지 않는 `<gameId>-<타석 번호>`.
- **제목**: 기록으로 확인되는 사실만 쓴다(상황, 대타, 마지막 이닝).
- **승부처 지수**: 실제 결과의 |WPA| 대신 엔진이 계산한 사전 기대 변화 E|ΔWP|(%p)를 보여준다. 파이프라인의 |WPA|는 장면을 고르는 데만 쓴다.
- **trust 리포트**: 같은 투수 규칙으로 다시 만든다.
**이유**: 장면 16개 중 2개의 투수가 틀렸다. 원자료 타석 10,999개 중 1,000개에 같은 문제가 있었다. 16개 장면 모두 타선 1~4칸에서 교체가 빠졌다. 실제 |WPA|는 결과를 미리 알려준다(8/23 장면: 표시 90.3 vs 사전 기대 11.4%p). `walkoff-slam` 같은 id도 결과를 드러냈다.
**트레이드오프**: 앱 데이터와 엔진 신뢰도 수치를 다시 만든다(Brier 값이 바뀔 수 있다).

### ADR-015: 다시 치르기는 멈추고 건너뛸 수 있다 (ADR-002 재생 보강)
**결정**: 재생 중에도 "건너뛰기"(남은 연출 없이 결과 반영)와 "처음부터"를 쓸 수 있다. 느린 연출은 승부처 타석(최대 3개)의 마지막 공에만 쓴다. 한 판에는 시드 하나로 만든 난수 생성기 하나를 이어 쓰고, 공마다 연속 시드로 생성기를 새로 만들지 않는다. 결과 화면은 자리 표시 없이 한 판의 끝(승패·평행우주 1,000경기·나비효과·봉인된 실제 결과·공유)을 보여준다.
**이유**: "경기 끝까지" 연출이 평균 41초, 최대 76초였는데 도중에 멈출 수 없었다. 끝나면 제목뿐인 결과 화면으로 가서 작동하지 않는 것처럼 보였다. 공마다 연속 시드를 쓰니 첫 난수 분포가 치우쳤다(χ²(99) 195.2 vs 단일 스트림 74.2).
**트레이드오프**: 같은 공유 링크라도 이전 버전과 재생 결과가 달라진다.

## 2026-09-15 실시간 전환

아래 결정은 앞 결정과 충돌하는 부분을 대체한다. 계기는 사용자 요청이다: "명장면이 아니라 실시간 야구 경기에 연동돼서, 야구를 보다가 '방금 이 상황에서 김도영이 똥이 마려웠다면 삼진 당했을 텐데'를 직접 할 수 있어야 재밌고 가치가 있다." 명장면 16개(`scenes.json`)와 나이트게임 화면(ADR-011·012)은 더 쓰지 않는다. ADR-014의 투구 시점 규칙(첫 투구의 투수, 교체를 반영한 타선, 결과를 드러내지 않는 id)은 중계 파서에 그대로 옮긴다.

### ADR-016: 세 가지 경기 종류와 되돌려보기 (PRD 명장면·한 판 흐름, ADR-015 경기 끝까지 대체)
**결정**: 경기 종류는 실시간·지난 경기·직접 만들기 셋이다. 셋 다 `Situation`(타석 직전 상태, 볼카운트, 양 팀 타선, 타자, 투수, 실제 결과 또는 null)으로 바뀌어 같은 타석 화면으로 들어간다. TMI는 이미 끝난 타석(실시간·지난 경기)이나 직접 만든 타석에 건다. 다음 타석 예언은 하지 않는다. 다시 치르기는 그 타석 하나(한 타석 쳐보기)뿐이며, 경기 끝까지 재생·기록 목록·승률 흐름 차트·확률 탭(타석·이닝·경기)은 없앤다. 큰 숫자는 실제 결과 사건의 타석 확률이고(직접 만들기는 출루 확률), 공격 팀 경기 승리확률 변화는 한 줄이다.
**이유**: 사용자는 보는 중에 떠오르는 '만약'을 가치로 봤다. 결과가 나온 타석에 거는 흐름이 기다림 없이 가장 짧고 사용자 예시와 같다. 경기가 없는 시간(심사·투표)에도 같은 화면을 쓰려면 지난 경기·직접 만들기가 정식 모드여야 한다. "경기 끝까지"는 평균 41초였고 후반은 합성 불펜이라 현실감이 낮았다.
**트레이드오프**: 끝까지 보는 긴장감이 사라진다. 타석 확률은 경기 승률보다 TMI 효과가 크게 보이는 단위라 과장처럼 읽힐 수 있다(경기 승률 한 줄과 등급 라벨로 균형을 잡는다).

### ADR-017: 네이버 중계 프록시와 캐시 (ADR-001 서버 로직, ADR-005 보강)
**결정**: `api/games.ts`(날짜별 경기 목록)와 `api/game.ts`(한 경기 요약: 상태, 이름·손, 타석 목록과 투구 행, 진행 중 타석)가 서버에서 네이버 `api-gw.sports.naver.com`을 부른다. 브라우저는 네이버를 직접 부르지 않는다(외부 Origin 요청은 403). 서버는 원문을 앱 계약 `LiveGame`으로 줄여서 돌려주고 `currentPlayersInfo` 같은 큰 필드는 버린다. 캐시 헤더는 진행 중 경기 `public, s-maxage=5, stale-while-revalidate=30`, 끝난 경기 `s-maxage=86400`, 경기 전 `s-maxage=60`, 목록 `s-maxage=60`이다. 인스턴스 안에서는 같은 경기 요청을 하나로 합친다. 함수 지역은 서울(`icn1`)이다. 파싱은 순수 모듈 `src/live`에 두고 서버 함수와 테스트가 함께 쓴다. 클라이언트는 화면이 보일 때만 진행 중 경기를 5초마다(경기 전·반이닝 사이 30초) 가져오고 종료되면 멈춘다. 네이버 연결이 실패하면 매치업 찾기(수집본)·직접 만들기로 안내한다.
**이유**: 보는 사람 수와 상관없이 네이버 호출을 경기당 5초 1번 이하로 묶어야 차단 위험이 작다. 원문은 이닝당 95~253KB(압축 없음), 경기당 최대 1.6MB라 휴대폰에 그대로 넘기기 무겁다.
**트레이드오프**: 비공식 API라 형식이 바뀌거나 서버 IP가 막히면 실시간·지난 경기 목록이 멈춘다. 문자중계 반영 지연에 캐시 5초가 더해진다. 원문 대신 요약을 전달하지만 권리 위험은 남는다(출처 표기, 사진·로고·영상 없음).

### ADR-018: 포수 뒤 중계 트래커 (ADR-011 시각 기준, ADR-012 카메라 대체)
**결정**: 시각 기준 시안은 `docs/design/broadcast/`다. 경기장 캔버스는 포수 뒤 망원 시점 투구 트래커로 그린다: 관중석 띠, 잔디·흙, 스트라이크 존 3×3, 구종 색 투구 궤적, 콜 색 투구 번호 원. 사람(투수·타자·포수·주심)은 그리지 않는다. 궤적은 실제 PTS 행을 쓰고 존 판정 면은 홈플레이트 앞면(y = 1.417ft)이다. 볼·스트라이크 콜은 행에 기록된 결과를 따른다. 트래커는 문서가 숨겨지면 진행 중인 연출을 즉시 끝내고, 제한 시간 가드와 주입 가능한 시계·requestAnimationFrame을 둔다. 토큰·글꼴은 시안 `style.css`를 따른다(숫자 Barlow Semi Condensed, 본문 Noto Sans KR). 나이트게임 경기장·인형 연출과 금속 테두리·포스터 글꼴은 없앤다.
**이유**: 사용자 평가가 "촌스럽고 현실성이 없고 한눈에 안 들어온다"였다. 실제 중계의 투구 트래커는 팬에게 익숙하고, 실제 궤적 데이터가 그대로 보인다. 사람 인형이 현실감을 떨어뜨렸다.
**트레이드오프**: 타구·주루 연출이 없다(결과는 콜과 자막으로 알린다). 기존 `stage/render`·인형 자세 계산과 그 테스트를 지운다.

### ADR-019: 만화 모드는 결과 비교 한 줄 (ADR-009 대체)
**결정**: 플레이 중 모드 전환은 없고 화면의 확률은 모두 현실 모드다. 결과 카드에 "만화 모드(효과 6배)였다면 N%" 한 줄만 두고 그 줄에 모드 라벨을 붙인다. 공유 이미지에는 현실 값을 크게, 만화 값은 라벨과 함께 작게 넣는다.
**이유**: "겉은 게임, 속은 팩트체크" 정체성을 지키면서 작은 효과를 크게 보는 재미는 남긴다.
**트레이드오프**: 만화 모드로 계속 노는 재미는 줄어든다.

### ADR-020: 판정은 TMI 카드 안에서 (PRD 판정소 대체)
**결정**: 판정소 탭을 없앤다. TMI 카드의 "진짜야?"가 판정(맞는 실측 변수, 학습·검증 수치)을 카드 안에서 연다. 실측 변수 전체 표와 엔진 신뢰도(Brier)는 "만든 이유"로 옮긴다. 하단 탭은 경기·만든 이유 두 개다.
**이유**: 판정은 기술력을 가장 잘 보여주지만 게임 흐름 밖에 있어 거의 보이지 않았다.
**트레이드오프**: 변수 목록을 한눈에 훑는 화면이 뒤로 숨는다.

### ADR-021: 모든 선수 데이터와 매치업 색인 (ADR-005 최소 요약 보강)
**결정**: `core.json`에 2026 시즌 기록이 있는 모든 선수(능력치 `rel`, 손, 시즌 기록 줄)와 팀 기본 타선(`teamLineups`)을 싣는다. 같은 id가 타자·투수 둘 다면 투수 기록은 `<id>`, 타자 기록은 `<id>:H` 키로 둔다. 투수 투구 표본은 투수당 최대 48행으로 줄인 `pitches.json`을 쳐보기를 처음 누를 때 불러온다. 매치업 찾기는 수집한 중계의 타석 색인 `matchups.json`(경기 id·타석 번호·이닝·초말·타자·투수·사건)을 매치업 화면을 열 때 불러온다. 원자료 수집은 `pipeline`의 수집 명령으로 로컬에서만 하고 커밋하지 않는다.
**이유**: 실시간·직접 만들기에는 어떤 선수든 나온다. 장면 선수만 싣던 146명으로는 대부분 리그 평균이 된다. 전체 선수를 실어도 약 124KB(gzip 약 28KB)다.
**트레이드오프**: 번들과 공개되는 요약 데이터의 범위가 커진다. 매치업 찾기는 수집한 기간만 된다. 시즌 기록은 수집 시점에 멈춘다.

### ADR-022: 익명 인기 TMI 집계 (PRD MVP 제외 '공개 랭킹' 부분 대체, ADR-007 보강)
**결정**: 해석이 끝난 TMI의 효과 키(`knob:<손잡이>:<대상>:<up|down>` 또는 `measured:<변수>`)만 `api/tally.ts`로 보내 경기별·날짜별로 센다. 문장·IP·기기 정보는 저장하지 않는다. 저장소는 Vercel Marketplace의 Upstash Redis이고 REST API를 `fetch`로만 부른다(새 npm 의존성 없음, 환경변수 `KV_REST_API_URL`·`KV_REST_API_TOKEN`). 키에는 이틀 TTL을 둔다. 환경변수가 없으면 503을 돌려주고 화면은 순위 칸을 숨긴다. IP당 분당 호출 수는 인스턴스 메모리로 제한한다.
**이유**: 같은 경기를 보는 사람들의 반응이 보이면 실시간의 재미가 커진다. 문장을 저장하지 않으면 실존 선수 TMI 모더레이션이 필요 없다.
**트레이드오프**: 반복 호출 조작에 약하다. 저장소 연결은 사용자가 Vercel 대시보드에서 해야 한다.

### ADR-023: 앱 데이터만 커밋하고 GitHub 빌드로 배포 (ADR-005 '생성물 커밋 금지' 부분 대체)
**결정**: Vercel은 GitHub에 push된 코드로 빌드한다. 빌드가 `import.meta.glob`으로 번들에 넣는 `data/build/app/*.json`(core·pitches·scenes·evidence·trust)만 커밋한다. `data/raw`(네이버·Open-Meteo 원자료)와 `data/build`의 나머지 중간 생성물은 계속 커밋하지 않는다. 데이터를 새로 만들면 `npm run data` 뒤 이 파일들을 함께 커밋한다.
**이유**: `data/`를 통째로 빼면 Vercel 빌드에 앱 데이터가 없어 "데이터를 기다리는 중" 화면만 뜬다. 이 파일들은 배포된 JS 번들로 어차피 공개되는 요약본이고, 크기도 약 400KB다.
**트레이드오프**: 공개 저장소 기록에 가공한 기록 요약이 남는다(ADR-005의 재배포 우려를 받아들인다). 데이터를 다시 만들 때마다 저장소 기록이 커진다.

### ADR-024: 서버 함수는 빌드 때 번들해 Build Output API로 낸다 (ADR-017 배포 보강)
**결정**: `api/*.ts`(테스트·`_lib` 제외)를 Vercel 빌드에서 Vite SSR 빌드로 함수마다 import 없는 ESM 한 파일로 묶고, Node `(req, res)` 어댑터를 씌워 `.vercel/output/functions/api/<name>.func/index.mjs`로 낸다. `.vc-config.json`은 `nodejs22.x`·`launcherType: Nodejs`·`regions: ["icn1"]`·`maxDuration`(verdict 60초, 그 밖 20초)이다. 정적 파일은 `dist`를 `.vercel/output/static`에 복사한다. Vercel 빌드 명령은 `npm run build:vercel`이고, `outputDirectory: dist`는 `.vercel/output`이 쓰이지 않을 때 정적 사이트라도 뜨게 하는 대비책으로 남긴다.
**이유**: 2026-09-15 운영 확인에서 `/api/interpret`가 500(FUNCTION_INVOCATION_FAILED)이었다. ESM 저장소에서 확장자 없는 상대 import(`./_lib/handlers`, `../../src/...`)와 JSON import를 Vercel Node 런타임이 풀지 못한다. 모든 `src` import에 `.js`를 붙이는 방법은 수백 곳을 바꾸고 병렬 phase와 충돌한다. Vite SSR 번들은 실험에서 모듈 12개를 import 없는 32KB 파일로 묶었고 Node에서 그대로 돌았다.
**트레이드오프**: Vercel이 `api/`를 알아서 함수로 만드는 기본 동작 대신 출력 구조를 우리가 책임진다. 로컬 `npm run build`와 배포 빌드가 한 단계 다르므로 `npm run check:vercel` 스모크 점검으로 메운다.

### ADR-025: 중계 시안 네 화면을 그대로 쓴다 — 명장면 다시 치르기 (ADR-016 화면 흐름·ADR-019·ADR-020 대체)
**결정**: 앱 화면은 `docs/design/broadcast` 시안의 로비·플레이·TMI 카드·결과를 구성·크기·정보량까지 그대로 옮긴다.
- 로비: 오늘의 명장면 카드(원정·홈 큰 점수, 주자·아웃, 타자·투수 시즌 기록, 승부처 지수 = 엔진 기대 변화 ADR-014)와 다른 명장면 목록. 하단 탭은 명장면·판정소·만든 이유.
- 플레이: 스코어버그 → 포수 뒤 트래커 → 승부 확률 판(경기·이닝·타석 탭, 현실·만화 ×6 전환, 큰 숫자, TMI 변화, 추이선, 승률 막대) → 걸린 TMI 줄(칩마다 효과와 그 TMI 하나의 승률 변화) → 도크(타석 끝까지·한 구 던지기·경기 끝까지). 실제 결과와 실제 투구는 경기가 끝날 때까지 숨긴다.
- 결과: 최종 점수와 결정 장면 한 줄, 평행우주 1,000경기(승·무승부·패와 TMI 없이 값), 나비효과, 눌러야 열리는 실제 결과.
- 경기 승리확률은 무승부를 더하지 않는다. 무승부는 막대 가운데 빗금과 보조 줄에 따로 보인다.
- 거부된 TMI는 TMI 칸(3개)을 차지하지 않고 이유만 알린다.
- 실시간 경기·지난 경기 타석 목록·직접 만들기(ADR-016)와 서버 함수(ADR-017·024)는 이번 배포 화면에서 뺀다.
**이유**: 2026-09-15 사용자가 빠르게 옮긴 한 타석 화면(db58f43)보다 오전에 본 시안이 낫다고 정했다("그냥 이전게 낫다", "되게 구체적으로 UI를 만들었으면"). 시안 흐름은 기존 재생·평가 코드(usePlayback·useSceneEvaluations)로 이미 돌아가 새 엔진 작업 없이 옮길 수 있다. 승리확률에 무승부 절반을 더하면 11회처럼 무승부가 흔한 장면에서 실제 승리확률보다 크게 보였다(9/10 11회말 42.1% 표시, 실제 승리 25.5%).
**트레이드오프**: 실시간 연동 기획은 뒤로 밀린다. 만화 모드 값이 결과 카드 밖(승부 확률 판)에도 보이므로, 모드 칩과 보조 줄 "만화 모드 · 효과 6배 과장"으로 늘 밝힌다(ADR-019 대체).

### ADR-026: TMI가 먼저 보이고, 사전으로 무엇이든 받고, 효과는 크게 (ADR-002 효과 크기·ADR-013·ADR-025 보강)
**결정**:
- 플레이 화면에 아직 TMI가 없으면 걸린 TMI 줄 자리에 노란 테두리 초대 판("방금 이 타석에 TMI 걸기")과 "바로 걸기" 칩을 둔다. 칩은 시트 없이 그 문장을 바로 건다. TMI가 생기면 칩 줄과 노란 "+ TMI 걸기"로 바뀐다. 초대 판·"+ TMI 걸기"로 시트를 열면 입력칸에 초점을 둔다. 시트 입력 줄 위에 "아무 말이나 한 줄이면 확률이 바뀌어요" 안내를 둔다.
- AI 키가 없으므로 규칙 해석을 기본 경로로 본다. 입력 정리(text.ts) → 안전 판정(safety.ts) → 절마다 대상 추론(targets.ts) → 개념 사전(lexicon.ts 핵심 개념 + lexiconDb.ts 일상 낱말 DB) → 부정·강도 → 실측 값 → 합치기. 사전에 없는 문장도 문장 분위기(없으면 해시)로 이번 타석 '상상' 효과 하나를 낸다. 민감 주제는 계속 거부하고, 주체를 모르는 민감 문장도 AI가 없으니 거부한다.
- 효과 크기: STEP 0.06 → 0.3, 현실 모드 상한 0.45 → 1.2, 만화 모드 상한 1.6 → 2.3(만화 배수 6은 그대로). 해석 세기는 사전 세기보다 한 단계 크게, "너무·완전"은 두 단계, "살짝·조금"은 사전 세기 그대로다(최대 3).
- 날씨·이동·휴식 개념은 실측 변수(‘진짜야?’ 판정용)와 효과 손잡이(가정)를 함께 낸다.

**이유**: 사용자 요청(2026-09-15): "TMI 거는 게 눈에 확 안 들어와", "AI API를 줄 수 없으니 사용자가 입력할 만한 많은 단어·문장을 DB에 담아 무엇을 입력하든 최대한 확률에 반영", "확률이 좀 많이 반영되었으면". 16장면 실측: 세기 −2 손잡이 하나가 타석 출루확률을 평균 1.4%p(STEP 0.06)에서 7.3%p(0.3)로, 경기 승률을 1.0%p에서 5.3%p로 움직인다.

**트레이드오프**: 현실 모드 숫자도 기록 근거보다 크게 과장된다. 그래서 손잡이 효과는 늘 '상상'·'그럴듯함' 등급과 함께 보이고, 기록 근거는 실측 변수 판정('진짜야?')으로만 말한다. 규칙 사전은 문맥을 틀릴 수 있어 말뭉치(`src/test/fixtures/tmiCorpus.ts`) 일치율로 관리한다.

### ADR-027: 트래커 카메라는 포수 눈높이, 투수 손은 늘 화면 안·백스크린 앞 (ADR-018 카메라 보강)
**결정**:
- 투구 트래커 카메라를 시안의 홈플레이트 30ft 뒤·높이 4.6ft에서 10ft 뒤·높이 4ft로 옮긴다.
- 구도(`frameTracker`)는 시안의 홈플레이트 폭 27%·지평선 14%를 기본으로 두고, 존 아래 끝은 자막(120px) 위, 투수 손(55ft·6.3ft)은 위 여백(높이 10%) 안에 오도록 지평선을 옮긴다. 둘 다 못 담으면 초점 거리를 줄인다.
- 가운데 외야 뒤에 어두운 백스크린(폭 90ft·높이 40ft)을 그린다.

**이유**: 사용자 요청(2026-09-15): "공이 날아오는 모습이 현실적이지 않아 너무 위에서 날아와". 플레이 화면 트래커(480×388)에서 기존 구도는 존을 자막 위에 올리느라 지평선을 캔버스 위로 밀었고, 투수 손이 캔버스 위 55px 밖이라 공이 화면 밖에서 떨어졌다. 캔버스 안에 들어와도 공은 존 윗변에서 존 높이의 1.06배 위, 관중석에서 나왔다. 새 카메라에서는 존 높이의 0.6배 위에서 나와 홈에 올 때까지 5.7배 커진다. 낮은 카메라에서 투수 손(약 6ft)은 늘 지평선 위에 보이므로, 실제 구장처럼 백스크린이 있어야 공이 관중석에서 나오지 않는다.

**트레이드오프**: 화각이 넓어져 마운드·내야가 시안보다 작고, 캔버스가 낮으면 존도 폭 27%보다 작아진다(480×388에서 23%). 사람을 그리지 않으므로(ADR-018) 공은 빈 백스크린 앞에서 나타난다.

### ADR-028: 서버 함수는 Vercel 기본 함수 빌드 그대로 — api가 닿는 모듈은 확장자 있는 import (ADR-024 대체)
**결정**: Vercel이 `api/*.ts`를 파일마다 JS로 옮겨(묶지 않는다) Node ESM으로 불러오는 기본 함수 빌드를 그대로 쓴다. 그래서 `api/` 함수에서 닿는 모듈(`api/_lib`, 그리고 `src/ai`·`src/domain`·`src/types` 가운데 닿는 파일)의 상대 import에는 `.js` 확장자를 붙이고(`'./text.js'`, TypeScript·Vite는 `.ts`로 푼다), JSON import에는 `with { type: 'json' }`을 붙인다. `api/_lib/nodeEsm.test.ts`가 함수가 닿는 파일을 같은 방식으로 임시 폴더에 옮겨 별도 node 프로세스에서 불러오고, 빈 본문 400·키 없음 503을 네트워크 없이 확인한다. 제한 시간은 `vercel.json`의 `functions`로 둔다(verdict 60초, interpret 20초). ADR-024의 Build Output API 번들(`build:vercel`·`check:vercel`)은 만들지 않는다. 배포 화면이 이 함수를 부르려면 Vercel 빌드 환경변수 `VITE_AI_API_BASE`(`/api`)가 있어야 한다(`src/app/platform.ts`). 2026-09-22 배포 번들에는 이 값이 없어(`apiBase` null) 브라우저가 `/api`를 부르지 않고 규칙 해석만 썼다.
**이유**: 2026-09-22에도 `/api/interpret`·`/api/verdict`가 GET·빈 POST 모두 500(FUNCTION_INVOCATION_FAILED)이었다. 로컬 `vercel build`(CLI 59.25.0) 출력 `interpret.func/api/interpret.js`를 Node에서 import하면 `ERR_MODULE_NOT_FOUND ... api/_lib/handlers`로, 그것을 고치면 `ERR_IMPORT_ATTRIBUTE_MISSING ... measured.json`으로 핸들러에 들어가기 전에 죽었다. 고칠 곳은 함수가 닿는 14개 파일의 import 50줄뿐이었고(ADR-024가 걱정한 '수백 곳'은 `src` 전체 기준), 프런트 번들은 해시까지 같다. 번들 방식은 Vercel이 `api/`에서 알아서 만드는 함수와 `.vercel/output`이 겹치는 문제, Node `(req, res)` 어댑터, 별도 빌드 명령을 새로 떠안는다.
**트레이드오프**: `api/`가 닿는 모듈에 확장자 없는 import를 새로 넣으면 배포에서만 다시 죽는다(Vitest·Vite는 풀어 준다). 위 테스트가 `npm run test`에서 잡는다. `src` 안에 확장자 있는 import와 없는 import가 섞인다. `phases/14-live-data`의 step 1·3(함수 지역·Build Output API)은 실행 전에 이 결정에 맞춰 다시 써야 한다.
